Records and values

The durable format separates application values from workflow metadata. IDs, statuses, retry policy, and ownership fields let the Store validate transitions without understanding the bytes of an input or result.

Audience: maintainers, adapter authors, and integratorsSource: records, values, identity types

Typed identities

Execution IDs, step IDs, worker IDs, and lease tokens are separate Rust newtypes over UUIDs. They share an encoding shape but cannot be accidentally passed in place of one another in typed APIs. Revision is a separate unsigned counter used for compare-and-swap.

OperationKey is a name and numeric version. It identifies which application code understands a durable execution. StepName identifies a checkpoint inside one execution. Step names contain 1–200 UTF-8 bytes and are compared exactly, without case folding or Unicode normalization.

Execution record

An ExecutionRecord contains the operation key; optional input and result; bounded metadata; status and revision; creation, update, start, and completion timestamps; optional cancellation request, lease, and failure. The record is the durable snapshot an adapter validates and changes atomically.

Execution completion stores the encoded result in the same transition that sets the terminal status. Failed execution records include a failure class, optional diagnostic string, and time. Cancellation does not retain a result.

Step record

A StepRecord stores its own step ID and name along with parent execution ID, status, attempt count, optional result, timestamps, next eligible attempt time, last failure, and retry-policy snapshot. The step identity survives retries; attempt number identifies which invocation ran.

A step result is only present after successful completion. A retryable failure stores the next eligible timestamp with the failure. Starting the next attempt increments the count, clears the prior failure and deadline, and records a new start time. The failure classification and timestamp remain available in the resulting step record until the next attempt starts.

Value codec

StoredValue consists of a codec identifier, schema version, and bytes. JsonCodec is the default and uses serde-json with schema version 1. A custom ValueCodec can encode application values in another stable format. The same codec and schema version must remain decodable after process restart.

Decode verifies payload size, codec identifier, and schema version before interpreting bytes. Unknown codec, version mismatch, corrupt bytes, or type mismatch returns an error. The runner must not treat a decode error as a missing completion: rerunning a completed effect could duplicate external work.

  • Maximum codec identifier: 64 UTF-8 bytes.
  • Maximum encoded value: 16 MiB.
  • Encoded values are validated when constructed and when deserialized.

Execution metadata

Metadata is a small map of labels intended for filtering and diagnostics, not for storing inputs or results. It is not required for correctness, and it is not part of execution creation identity. The first successful create stores it; a compatible create retry returns the original record and its metadata.

  • At most 64 labels.
  • Keys are non-empty and at most 64 UTF-8 bytes.
  • Values are at most 256 UTF-8 bytes.
  • Total key and value bytes are at most 8 KiB.

Inputs, results, metadata, and diagnostics may contain sensitive data. The core avoids logging serialized values, but storage adapters and applications still own access control, encryption, retention, and diagnostic redaction.

Idempotency keys

The step key identifies one logical step across retries. The attempt key identifies a single attempt and changes when the attempt number changes. Both are derived from the execution UUID and exact step name; the attempt form also includes the attempt number. Domain tags distinguish their intended use. Fields are length-prefixed, hashed with SHA-256, and encoded as unpadded base64url with an rs1_ prefix.

The hash makes keys compact and opaque; it does not provide authentication, authorization, or a mathematical guarantee against collisions. Do not use an idempotency key as a secret or capability.

Timestamps and time

Timestamp stores Unix milliseconds. Different decisions use clocks at different boundaries: the adapter clock is authoritative for lease expiry and whether persisted retry deadlines are due. The runner currently supplies timestamps and computes proposed retry deadlines. See clock authority for the consequences of skew and the adapter design requirement.

Error categories

Errors indicate which layer needs attention
Error Meaning Typical response
Operation User-supplied operation or step body returned an error Apply operation policy; reconcile effects before another attempt
Store unavailable Backend could not provide a reliable response Retry the identical mutation with the same mutation ID, then recover by reloading/resuming
Conflict Stale owner, revision, state, identity, policy, or attempt Do not blindly retry; reload and follow current state
Corrupt Persisted record violates invariants or cannot be validated Stop normal execution and repair or investigate the record
Value Encoding, codec, schema, size, or decode problem Use the compatible codec/version; preserve completed state
Busy / terminal Execution has another live owner or cannot be claimed in its current state Wait for dispatch eligibility or treat the terminal result as final

Retention and purge

The Store can purge only completed or cancelled executions, removing their steps and progress together. Pending, running, and failed records may still be needed for resume and are rejected. Applications decide when terminal history is safe to delete. Large referenced artifacts need a retention period at least as long as the execution history that refers to them.

Reference store and conformance

reference::MemoryStore is an in-process implementation for development and tests. Its ManualClock controls lease and retry eligibility. FaultInjector can simulate a failure before commit or a commit whose response was lost.

Adapter authors can run conformance::run_store_scenarios against a fresh store to check shared behavior. The scenario matrix is summarized in the conformance coverage document. A passing in-memory store does not prove an adapter's database transactions are atomic; each adapter must pass the same scenarios.
