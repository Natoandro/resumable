Using the library

Retries and external effects

Retry policy controls whether another step attempt may run. It cannot tell whether an external system already performed an action. Stable idempotency and reconciliation close that gap.

Audience: library integratorsRelated: Store and ownership

Attempts and policy

A step starts at attempt 1. max_attempts counts the total number of attempts, including the first. The default StepOptions permits one permanent attempt. To retry, mark the operation error retryable and choose a policy: 

let options = StepOptions {
    retry_policy: RetryPolicy {
        max_attempts: 4,
        backoff: Backoff::Exponential {
            initial: Duration::from_secs(2),
            factor: 2.0,
            max: Duration::from_secs(30),
            jitter: true,
        },
    },
    retryable: true,
};

ctx.step_with("send-message", options, |step| async move {
    provider.send(request, step.idempotency_key()).await
}).await?;

The retry policy is stored atomically when the step first begins. Later calls with a different policy conflict rather than silently changing the meaning of existing history. A retryable failure is stored with its failure classification and next eligible timestamp.

A scheduled retry releases the execution lease and marks the execution failed. The caller gets the operation error and must explicitly call resume after the deadline; the core does not sleep or run an internal scheduler. The Store checks eligibility against its authoritative clock, and the original retry policy remains fixed across attempts.

Stable keys

Each step has a stable key derived from its execution ID and exact step-name bytes. The key stays the same across attempts and can be sent as an external provider's idempotency key. Each attempt also has a distinct attempt key, which is useful for logs or systems that need to distinguish retries.

Keys are domain-separated, length-prefixed tuples hashed with SHA-256 and encoded as unpadded base64url with the rs1_ prefix. They do not include input values or secrets. The step name is part of durable identity, so renaming it also changes the external idempotency key.

Reconcile the crash window

If an external request can be repeated safely, send the same stable step key on every attempt. A provider that retains idempotency records can return the original result. If the provider lacks idempotency support, query its state using a deterministic resource identity and verify that the existing result matches before deciding to reuse it.

Attempt keys are not substitutes for step keys when an effect should happen once per logical step: a new attempt key intentionally identifies a different attempt. Use it only when each attempt itself should have a distinct external identity.

Retention matters. Provider deduplication lasts only as long as its idempotency record. After that window, the application must reconcile external state or deliberately choose a new identity. The library cannot prevent an old request from being repeated after provider retention expires.

Leases are not exactly-once execution

A lease prevents a second worker from claiming live work. If a worker pauses beyond lease expiry, another worker can begin a new attempt while the first request is still in flight. Fencing protects resumable's store from stale writes; it cannot cancel a network request already sent to a provider.

Design effects to tolerate duplicate calls. Use a provider key, deterministic object key, conditional write with fencing generation when supported, or application-owned reconciliation. See fencing and leases for the storage boundary.

Failure types

Step body errors are classified as retryable only when StepOptions.retryable is true and attempts remain. Otherwise the failure is permanent. The diagnostic stores the error's display text; do not include secrets or sensitive payloads in errors. Store failures are separate from operation failures and can mean that the outcome of a write is uncertain.

When completion is uncertain, the Store contract uses a stable mutation ID to resolve a repeated identical write. This protects the durable record from duplicate attempt increments or conflicting completion. It does not deduplicate the external effect; that uses the step's idempotency key.
