Implementation

Store and ownership

The Store is the durable authority for execution records. Its methods are state transitions, not generic row updates: each one checks its preconditions and commits all related changes as a single operation.

Audience: Store adapter authorsSource: Store trait

Store boundary

The core defines the Store trait and typed requests. An adapter owns the database schema, transactions, query implementation, and authoritative clock. The trait uses native async-compatible methods that return Send futures; the core is statically dispatched and does not require boxed futures or dyn Store.

The Store does not own application dispatch, operation selection, authorization, provider calls, or discovery of pending executions. The application decides which operation closure matches a stored OperationKey and when a worker should call resume.

Atomic transition requirements

Creation compatibility, claim, begin attempt, completion, failure, cancellation, heartbeat, and purge each have to be serialized with concurrent changes. A relational adapter normally uses a transaction and row locks or conditional updates. The implementation mechanism can vary, but the observable outcomes cannot.

Lease guard

Every owner mutation carries a LeaseGuard: execution ID, worker ID, lease token, fencing generation, and expected execution revision. The Store validates these as a unit against the current record. A token alone is not enough: the generation distinguishes successive owners, the expiry check excludes stale time windows, and the revision detects intervening writes by the same owner or another authorized transition.

Fencing and leases

A live lease cannot be stolen. Once its expiry is reached according to Store time, another worker may claim the execution and gets a fresh random token and a greater generation. The previous owner's writes are rejected even if the old process resumes after a pause.

Lease duration is a liveness choice, not proof that an external request stopped. If a step body runs longer than its lease and no heartbeat occurs, another worker may begin a replacement attempt. The Store guarantees only that one generation can mutate the current record.

Every acquisition invocation has a fresh claim ID. Retrying a lost response reuses the same ID, worker, and requested duration; a different invocation sees Busy even when its worker matches. The execution retains its last generation after failure clears the lease, so resumed work always gets a greater external fencing token.

Mutation IDs and lost responses

Each write request includes a random MutationId. The Store records the request and its committed result. If the server commits and the network loses the response, repeating the same mutation ID with exactly the same request returns the original result—even if the lease expired after commit. Reusing that ID with different request data conflicts.

This is request idempotency at the persistence boundary. It prevents a repeated begin_step from incrementing attempts twice and lets the runner learn whether completion committed. It is separate from external idempotency keys, which identify a provider effect. Mutation receipts need a retention policy long enough to cover ambiguous retries; purging an execution can remove the history needed for later resume.

Clock authority

The Store clock decides whether a lease is expired and whether a retry is eligible. An adapter must read its authoritative time as part of the atomic mutation; PostgreSQL adapters would typically use a database time function rather than trust the worker's clock. The reference store accepts a Clock, including a ManualClock for deterministic scenarios.

The runner currently computes a proposed retry timestamp before it sends the failure request. The Store compares that persisted deadline against its own clock on acquisition and step start. Clock skew can therefore affect the chosen deadline, but cannot authorize an expired lease or bypass the Store's due-time comparison. Adapter designs should keep worker and database time aligned or move deadline calculation into the atomic store transition.

Store errors

StoreError::Unavailable means the backend could not report a reliable outcome. The runner retries some mutations once using the same request and mutation ID. Conflict covers stale ownership, state, revision, or incompatible identity. Corrupt means persisted data violates its record invariants. Conflicts and corruption are not transient failures to retry blindly.

Application transactions

The portable Store contract does not require a shared transaction with application data. An adapter may expose a transaction extension when both use one database, allowing a domain write and execution creation to commit together. That extension is adapter-specific and must not leak into the core Store API.

Current adapter state

The PostgreSQL adapter implements durable storage, migrations, and runnable discovery. reference::MemoryStore provides in-memory storage for tests and examples.
