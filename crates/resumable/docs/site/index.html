Durable execution for Rust

Operations that can continue after a restart

resumable records the useful boundary between application code and the work that must survive a process stopping: named steps, their attempts, and their completed results.

Core libraryv0.1 designIntegrators and maintainers

What the library provides

A durable execution has an identity, operation key, input and result envelopes, lifecycle status, revision, and optional lease. The application defines the operation function. Inside it, calls to named steps mark the points where output becomes durable.

After a process stops, the application loads the execution and invokes the operation again. resumable provides the stored input to that function. When execution reaches a step already marked complete, the core decodes and returns its recorded result without calling the body. The function can then continue at the next unfinished step.

Guarantee boundary. A completed step is not intentionally repeated by resume. A side effect can still happen twice if it succeeds externally and the process stops before the completion record is committed. Use stable identities and reconciliation for that window.

What it does not provide

The core is not a scheduler, queue, broker, or worker service. It does not discover runnable executions or start workers after a deployment. Applications own dispatch, authorization, and external clients. It does not capture Rust futures or promise exactly-once execution of arbitrary external effects.

The portable crate depends on the application-provided Store and does not require a specific async runtime. The reference in-memory store helps development and testing, but is not durable storage. The Planum adapter crate is currently a scaffold; production PostgreSQL persistence is not implemented yet.
