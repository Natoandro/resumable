Using the library

Operations and steps

An operation is ordinary Rust code. An execution is one durable instance of that operation. Named steps mark the results the code can reuse after a restart.

Audience: library integratorsRelated: retries and effects

Operation, execution, step

These terms describe different layers:

  • Operation: a versioned kind of work, such as build-report. The operation key is code identity: a name plus version.
  • Execution: one durable request to run an operation. It has a stable execution ID, input, status, and eventually a result or failure.
  • Step: a named durable checkpoint inside an execution. The pair of execution ID and exact step name identifies it.

The operation function is not serialized. On a later run, application code must supply a compatible function for the stored operation key. Increment the operation version when new code cannot safely interpret earlier stored data or step history.

Starting an execution

Engine::start creates a random execution ID. Use start_with_id when a domain event or database row already provides a stable identity. Both APIs persist the encoded input before invoking the operation, and the runner decodes that stored input before calling user code. 

let engine = Engine::new(store);
let operation = OperationKey::new("build-report", 1)?;
let (execution_id, report) = engine
    .start_with_context(operation, request, |request, ctx| async move {
        let source = ctx.step("load-source", |_step| async move {
            load_source(request.source_id).await
        }).await?;

        ctx.step("render", |_step| async move {
            render_report(source).await
        }).await
    })
    .await?;

The operation closure is FnOnce: it runs once per call to start or resume. Step bodies are Fn factories: a new future can be created for each attempt. Capture values that can be borrowed or cloned for another call. A value that should survive a restart should be returned by a prior step or reconstructed from durable application data.

What makes a step durable

For each call, the runner checks the stored step. If it is completed, the runner decodes and returns its stored result. Otherwise it atomically begins an attempt, calls the body, encodes the output, and asks the store to commit completion. Only after completion commits does the step call return success.

Code between step calls is not checkpointed. On resume it executes again. Keep such code deterministic or safe to repeat, especially if it has an external side effect. Place a durable step boundary around work whose output needs to be reused.

Step names are durable identifiers

A step is unique by (execution_id, step_name). Names are compared as exact UTF-8 bytes; no Unicode normalization is applied. Names must contain 1–200 UTF-8 bytes. Treat names as persistent identifiers, not labels for a user interface.

If a deployed operation changes upload to upload-v2, an old execution has no completed result under the new name. It will run the new step. If that change is incompatible with old execution data, route old operation versions to compatible code or deliberately start a new execution.

Inputs and results

Inputs, step results, and execution results are stored as opaque envelopes: codec ID, schema version, and bytes. The default JSON codec is serde-json version 1. A completed value must still have a compatible decoder when a later process resumes it. A decode error does not erase a completed step or authorize replaying its body.

Values are limited to 16 MiB. Store large artifacts elsewhere and persist a stable reference such as an object key, content hash, or domain ID. The referenced object must remain available for as long as a future resume may need it.

Resume and dispatch

resume loads the execution by ID and checks the operation key. It then runs the supplied operation function with the stored input. Terminal completed executions return their stored result. A failed execution is rejected by default; set FailedExecutionPolicy::Resume to allow the engine to try claiming a failed execution again, subject to the store's state and retry checks.

resumable does not find or schedule pending work. Your application must persist the execution ID somewhere it can recover, decide when to call resume, and ensure only authorized workers do so. A queue can wake workers, but it is not the durable source of truth unless it participates in the same persistence guarantees.

Current API boundaries

The current core provides direct start/resume, named steps, persisted values, step retries, leasing, and result reuse. Cancellation requests and heartbeat/progress storage exist at the Store layer, but the runner does not yet expose cooperative cancellation or progress through StepContext. See execution state model for the distinction.
