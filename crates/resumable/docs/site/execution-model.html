Implementation

Execution state model

The runner describes one execution at a time. Durable records hold lifecycle state, while the Store arbitrates ownership and commits each transition atomically.

Audience: maintainers and adapter authorsSource: execution record

Execution and step states

An execution begins Pending. A worker claim moves it to Running. It then reaches Completed, Failed, or Cancelled. Completed and cancelled are terminal. Failed means execution stopped with an operation error; explicit application policy may allow another claim if the stored step failures and retry timing permit it.

A step is identified by its execution and name. Its status is Pending, Running, Completed, Failed, or Cancelled. The first attempt changes the counter from zero to one. A completed step cannot be started again. A failed retryable step can begin another attempt when due and when the execution is claimed again.

Revisions protect snapshots

Every execution record has a monotonically increasing revision. A runner loads a revision, performs a transition with that expected revision, and refreshes its local guard after successful step writes. The Store checks the revision in the same atomic operation as the change. If another actor changed the record first, the stale mutation conflicts instead of overwriting newer state.

Revision is a compare-and-swap version for the whole execution record. Step writes increment it because step progress changes the execution's durable history. Revisions do not replace lease fencing: they answer different questions. Revision asks “is this still the state I read?” Generation asks “is this still the current owner?”

Lease and fencing generation

A lease records the worker, claim ID, requested duration, random lease token, generation, and expiry timestamp. The Store checks all of these, along with expected revision, on every owner mutation. When a lease expires, a new claim gets a greater generation and a fresh token. The old worker is fenced out even if it wakes later.

The expiry check uses the Store's clock inside the atomic mutation. Reaching the expiry time itself means the lease is no longer valid. A heartbeat can extend a valid lease, but cannot revive an expired one.

Fencing only protects systems that check the generation. The resumable Store can reject a stale worker's write; an unrelated mail provider or object store cannot know about that generation unless the application passes it and the external system enforces it.

Why v0.1 steps are sequential

One execution has one lease and one revision stream. Step calls are sequential in v0.1, so a step body cannot race another step body in the same execution. This gives a simple order for revision refresh, cancellation observation, and result reuse. Parallelism belongs across executions; parallel branches would need a different ownership and merge contract.

Cancellation and progress support

The record and Store model can persist cancellation requests. A request cancels a pending execution immediately. For a running execution, the Store records a request timestamp; finishing after that timestamp produces a cancelled record and does not retain an execution result. A request that arrives after a terminal state leaves it unchanged.

The current runner does not poll cancellation or expose a cancellation token from StepContext. A running body therefore cannot yet cooperatively stop between effects. The Store can persist a heartbeat and optional progress value, but the current execution context does not provide a heartbeat/progress API. These are model and Store capabilities, not completed end-to-end runner features.

Current limit. Do not assume an active run will stop promptly after cancellation or automatically renew its lease during long work. The worker currently has a configured lease duration but no runner heartbeat loop.

What happens after lease loss

A body already running in Rust is not forcibly aborted by the Store. Its next attempt to mutate resumable state fails when the guard is stale or expired. If the external action completed during that interval, the new owner must use the step's stable key or reconcile the external result before it repeats the action.

Execution result and failure

The execution result is encoded and persisted atomically with the transition to completed. If cancellation is already recorded, the final status is cancelled and no execution result is kept. An operation error outside a step stores an execution failure and releases the lease. A step error records failure details on that step; if retry is eligible, the step and execution return to pending after the runner exits.
